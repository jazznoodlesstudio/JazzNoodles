> 我把系統開發生命週期（市場調查 → 需求訪談 → PRD → SA → SD → 開發 → Code Review → QA → 自動化測試 → 手冊，外加 Bug 循環）拆成專職 agent，由一位只負責調度的 Orchestrator 指揮。這個系列記錄那套設計怎麼來、為什麼這樣設計，以及哪裡還沒做完。

## 這個系列在講什麼

一開始我的做法很直覺：把需求丟給 AI，請它「從 PRD 一路做到手冊」。結果文件之間對不上、改一處不知道動到哪裡、進度只存在對話裡。

後來我改成另一種做法：==每個階段一位專職 agent，agent 之間不直接對話，只傳產物檔案，由一位不下場的裁判決定誰接下一棒==。

這個系列是整套設計的筆記，共五篇。它不是教你裝某個工具，而是講**設計取捨**：哪些東西要拆、哪些要落檔、哪裡一定要讓人簽名。

---

## 用接力賽來想：Orchestrator 是不跑步的裁判

這個系列會一直用一個比喻：**接力賽**。

接力賽輸贏常常不在跑得多快，而在交棒順不順。好的隊伍棒子不會掉，每個人清楚自己跑哪一段，裁判盯著交接區。

| 接力賽 | 我的系統 |
|---|---|
| 選手 | 專職 agent（PRD、SA、SD、開發……） |
| 每個人的賽道 | 「只讀宣告的輸入、只寫自己的輸出」 |
| 接力棒 | 產物檔案（PRD.md、SA.md、程式碼……） |
| 棒子上的編號 | 產物的 hash 指紋 |
| 裁判 | Orchestrator，自己不跑，只看交接 |
| 裁判的記分板 | STATE.json 與 STATUS.md |
| 「這一棒要先停下來簽名」 | 人工核准閘 |
| 換了跑道、換了場地 | 從 Claude Code 遷移到 Agent SDK |

> [!tip] 比喻只用來開門
> 每篇我都會先用接力賽講直覺，再換回正式的設計語言。

## 整個流程一張圖

![[agents-00-relay.svg]]

主流程是 PRD → SA → SD → 開發 → Code Review → QA → 自動化測試，手冊依賴 PRD 與實際程式。市場調查與需求訪談是選用階段，小修可以跳過。文件階段每份產出後停下來等人工核准，開發之後則自動接力。

## 這套框架目前做到哪

這個部分我想先說清楚，免得讀起來像「已經全部完成」：

| 項目 | 狀態 |
|---|---|
| 十二個 agent（市調、訪談、PRD、SA、SD、開發、Code Review、QA、自動化測試、手冊、Bug 回報、Bug 修復） | 已實作 |
| Orchestrator、變更傳播、狀態看板 | 已實作 |
| Release、Security Review | 規劃中，視專案需要再建 |
| UX Review | 已討論定案，尚未建 |
| 接真實 Jira | 待辦（目前用本地模擬） |
| 遷移到 Agent SDK 常駐服務 | 待辦 |

框架已經在兩個專案上跑過，其中一個走完整條流程。遷移到 Agent SDK 那一步還沒做，第 05 篇講的四條規則是為它預留的路，不是已經驗證的成果。
