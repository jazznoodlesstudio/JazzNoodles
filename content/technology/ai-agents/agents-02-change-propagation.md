> [!abstract] 這篇的重點
> 接力賽最怕的不是選手跑得慢，而是**棒子被換了，下一棒還拿著舊的**。解法是替每個產物記下「我是依據哪一版上游做的」，上游一變，下游自動被標成過期。

## 情境

站會上，產品負責人隨口說：「匯出功能順便加上 CSV 好了。」

大家點頭。我回到座位，把 FR-07 加進 PRD，存檔。

兩週後，QA 測匯出功能，發現系統設計文件裡根本沒有 CSV 的資料流，程式碼也沒有。小安說：「沒有人告訴我 PRD 改了。」

他沒有說錯。PRD 改了，SA 沒改，SD 沒改，程式碼當然更沒改。三份文件各自停在不同的時間點。

---

## 問題漏在哪

> [!failure] 漏洞一：靠人記得
> 「改了 PRD 要記得通知下游」是一條只會在忙的時候被忘記的規則。

> [!failure] 漏洞二：全部重寫的雪崩
> 反過來，如果上游一變就要求下游整份重寫，人工核准過的內容會被洗掉，成本也不成比例。

> [!failure] 漏洞三：不知道誰依賴誰
> 手冊到底依賴 PRD 還是依賴程式碼？QA 計畫依賴誰？沒有一張明確的依賴表，就沒辦法機械式地判斷「這次該動誰」。

## 解法：依賴圖＋指紋＋STALE

### 第一步：把依賴關係寫成表

```text
MARKET-SURVEY ─→ INTAKE ─→ PRD ─→ SA ─→ SD ─→ Code ─→ 自動化測試程式
                                   │             ├──→ Code Review 報告
                                   │             └──→ QA 測試計畫/報告
                        PRD、Code ─────────────────→ 使用者手冊
```

| 產物 | 直接上游 |
|---|---|
| PRD | INTAKE、MARKET-SURVEY（選用） |
| SA | PRD |
| SD | SA |
| Code | SD |
| QA 測試計畫 | PRD（驗收條件）、SA |
| 自動化測試程式 | QA 測試計畫、Code |
| 使用者手冊 | PRD、Code（實際行為） |

### 第二步：每個產物記下「我是依據哪一版上游」

```json
"SA": {
  "version": 3, "hash": "d4e5f6", "status": "APPROVED",
  "upstream": { "PRD": "a1b2c3" }
},
"SD": {
  "version": 1, "hash": "778899", "status": "STALE",
  "upstream": { "SA": "OLD_HASH" }
}
```

- `hash`：產物內容的指紋（用 `git hash-object` 取前 12 碼；程式碼用 commit hash）
- `upstream`：產出**當下**所依據的上游指紋

規則只有一條：==任何一個上游的現行指紋，不等於我記錄的值，我就是 STALE。==不需要 AI 判斷，是純粹的比對。

### 第三步：傳播演算法

1. 某產物改完，更新它的 version 和 hash
2. 掃依賴表，直接下游的 `upstream` 指紋對不上的，標成 `STALE`，丟進 `pending_updates`
3. 依拓撲順序（SA → SD → Code → 測試／手冊）一個一個派工
4. 派工訊息附上**上游的 diff**，並要求「評估影響範圍，只更新受影響的章節」
5. 文件類產物更新後，仍要過人工核准，才繼續往下傳

### 第四步：允許說「不關我的事」

這一步最關鍵。下游 agent 如果判斷這次變更不影響自己的產物，可以回報 `NO_CHANGE`。Orchestrator 就把它的 `upstream` 指紋更新成新值、解除 STALE。

```markdown
若收到「上游 diff + 影響評估」任務且判斷不影響 SA，回覆 NO_CHANGE。
否則先列出「受影響章節清單」，只改這些章節，不整份重寫。
```

沒有這一步，每次上游動一個標點，下游都要重寫一遍，這就是前面說的雪崩。

## 改完之後

回到那個站會。這次我把 FR-07 加進 PRD，Orchestrator 立刻跑了一次比對：

- SA、QA 計畫：`upstream` 指紋對不上，標 STALE
- 手冊：依賴 PRD，也標 STALE
- 其餘產物：不動

sa-agent 收到任務，列出受影響章節，只新增一個 use case，SA 從 v3 到 v4。我簽名核准，SD 才開始被叫醒。手冊 agent 看了 diff，這次只動「匯出」那一章。

兩週後 QA 不會再發現缺口，因為缺口在 PRD 存檔的當下就被標出來了。

## 還沒解決的事

> [!warning] 兩個誠實的風險
> - **`NO_CHANGE` 可能判錯。** 下游判斷「不受影響」若判錯，就會漏更新。我打算在 QA 階段加一致性抽查：比對文件與程式行為。
> - **文件膨脹後，粒度不夠細。** 實戰中 SA 曾長成多冊，一冊一個指紋太粗，變更傳播的粒度需要更細的約定。

## 速查表

| 機制 | 解決的問題 | 容易搞混的地方 |
|---|---|---|
| 依賴表 | 誰依賴誰要明確 | 手冊依賴「實際行為」，不只是文件 |
| `hash` + `upstream` | 機械式判斷是否過期 | 記的是「產出當下的上游版本」，不是現在的 |
| `STALE` | 標示待更新 | STALE 不等於要重寫 |
| `NO_CHANGE` | 避免重寫雪崩 | 需要抽查，防止誤判 |
| diff-based 更新 | 保護已核准內容 | 先列受影響章節，再動手 |

> [!tip] 一句話記住
> ==讓每個產物記得自己是跟著哪一版上游做的，過期就不用靠人記得。==
