## 情境

一個多 agent 研究系統收到「比較三家供應商的 2025 年交期」。主 agent 對三個 subagent 各下了一句指令：「研究供應商交期」。結果一個 subagent 查了 2021 年的舊資料，另外兩個查了同一家公司，第三家沒人查。

問題出在**委派的說明太短**。Anthropic 在自家多 agent 研究系統的工程文章裡提到同類問題：指令太模糊時，subagent 會誤解任務或重複彼此的搜尋。

Domain 1 的多 agent 題型，核心是：==主 agent 怎麼拆、怎麼交代、中斷後怎麼接、怎麼不讓 context 爆掉。==

---

## 考點 1：動態拆解子任務（目標 #4）

### 用樂團來想：編曲者看到曲目才分配聲部

固定曲目可以事先把聲部分好。但現場客人點歌，編曲者得看歌的結構，才決定要幾個樂手、各自負責哪段。

### 正式一點：固定流程 vs 動態拆解

| | 固定流程（workflow） | 動態拆解（orchestrator-workers） |
|---|---|---|
| 子任務 | 事先寫死 | 由 orchestrator 看輸入決定 |
| 適合 | 步驟可預測，例如固定的「擷取 → 驗證 → 入庫」 | 無法預測要幾步，例如「修改會牽涉幾個檔案」的程式變更、多來源研究 |
| 代價 | 彈性低 | 協調複雜度高、token 用量大 |

Anthropic 的說明是：orchestrator-workers 與平行化（parallelization）外型相近，關鍵差別在於子任務**不是預先定義，而是由 orchestrator 依輸入決定**。

### 委派時要交代什麼

Anthropic 的研究系統提到，每個 subagent 至少需要：

1. 明確的**目標**
2. 期望的**輸出格式**
3. 可用的**工具與資料來源**指引
4. 清楚的**任務邊界**（哪些不用做、別人負責什麼）

缺了這些，結果就是情境裡的重複與遺漏。另外也要**依問題複雜度決定規模**：簡單查詢一個 agent 就夠，不要為小事開十個 subagent。

> [!failure] 陷阱 1：指令只有一句話
> 「研究供應商交期」沒有範圍、年份、輸出格式，也沒說明同伴負責什麼。修正：每個 subagent 的任務描述寫明對象（哪一家）、時間範圍（2025）、輸出格式（交期天數＋來源）、邊界（不做價格比較）。

> [!failure] 陷阱 2：什麼都用多 agent
> 單一路徑、步驟固定的任務，用多 agent 只會增加 token 與協調成本。判斷標準是「子任務是否真的獨立且數量不確定」。

## 考點 2：結構化交接包（目標 #2）

### 用樂團來想：換班的樂手只看得到譜上寫的

下一班樂手沒聽過上一班彈了什麼，他唯一的資訊是交班時留下的那張紙。紙上沒寫的，他就不知道。

### 正式一點：agent 之間（或 agent 與人之間）交接，要帶什麼

當 agent 把案件升級給人工，或把工作交給另一個 agent，接手方**看不到**之前的對話。所以交接包要自己說清楚，至少包含：

| 欄位 | 內容 | 缺了會怎樣 |
|---|---|---|
| 背景（context） | 任務目標、使用者要什麼 | 接手方重問一次，或做錯方向 |
| 已完成的發現（findings） | 已查到什麼、做過什麼、結果如何 | 重工，或重複執行有副作用的動作 |
| 授權與狀態 | 已經授權了什麼、哪些動作已執行（例如已退款） | 重複退款、越權操作 |
| 待決事項 | 為什麼交出來、需要對方決定什麼 | 接手方不知道要做什麼 |

![[ccarf-02-handoff.svg]]

重點是用**結構化欄位**，不是把整段對話原文貼過去。原文冗長、重點被埋住，結構化摘要讓接手方一眼看到該看的。

> [!failure] 陷阱 3：交接包只有「請處理這個客戶」
> 接手方得從頭問，客戶要重講一遍，而且接手方不知道上一步已經退過款。

## 考點 3：session 續接（目標 #3）

工作被中斷（關掉終端機、當機、隔天再做），要接著做。Claude Code 提供的方式：

| 做法 | 作用 |
|---|---|
| `claude --continue` | 接續目前目錄最近一次的 session |
| `claude --resume [名稱或 ID]`、`/resume` | 選擇某個過去的 session 續接 |
| `--fork-session`、`/branch` | 從某個 session **分支**出去，不影響原本的 |

續接時會還原：對話歷史、工具結果、模型、agent、權限模式。**不會還原**的有：`--mcp-config`、`--add-dir` 這類啟動旗標，需要重新帶。

### 考試重點：中斷後的世界可能已經變了

兩個細節：

1. **被中斷的工具呼叫**會顯示為被截斷，Claude 必須先**確認它到底有沒有生效**，再決定要不要重跑。直接重跑，可能造成重複寫入或重複扣款。
2. 續接之前，如果檔案在這段時間被改過，舊的分析結果可能過期。比較好的做法是**告訴 agent 哪些檔案變了，讓它針對性地重新分析那些部分**，而不是整個重來，也不是假設舊結果仍然正確。

另外一個取捨：如果舊 session 裡塞滿了過時的工具結果，續接後效果可能不如**開新 session ＋ 用結構化摘要帶入重點**。這時續接的價值低於乾淨的 context。

> [!failure] 陷阱 4：續接後直接重跑上一步
> 上一步是「寫入資料庫」，session 在中途斷線。直接重跑可能寫入兩次。應先查證上一步的結果。

## 考點 4：context 管理與 subagent 隔離（目標 #15）

### 用樂團來想：樂譜架只有那麼大

一個樂手的樂譜架一次只放得下幾頁。要演很長的曲子，要嘛換譜，要嘛分給不同樂手各演一段、最後只交回「摘要」。

### 正式一點

- **subagent 有獨立的 context window**，不會繼承主 agent 的對話歷史，完成後只回傳摘要給主 agent。大量搜尋、讀檔、跑測試的雜訊留在 subagent 裡，不會佔用主 context。
- Claude Code 內建的 **Explore** subagent 是唯讀的探索用途；也可以自訂 subagent，限制它能用的工具。
- **scratchpad（暫存檔）**：把中間結果、計畫、進度寫進檔案，context 滿了或重開 session 後可以讀回來。Anthropic 的長時間運作 agent 實務就用進度檔記錄做了什麼。
- **針對性讀取**：先用搜尋找到相關段落再讀，不要整檔灌進 context。

| 想解決的問題 | 對應做法 |
|---|---|
| 探索性工作的雜訊太多 | 交給 subagent，只收摘要 |
| session 很長，前面細節會被擠掉 | 寫 scratchpad／進度檔；必要時 `/compact` 或開新 session ＋ 摘要 |
| 大檔案只有一小段相關 | 針對性讀取，而非整檔讀入 |
| 子 agent 產出很大、經過主 agent 轉述會失真 | 讓 subagent 寫檔，只回傳檔案參照 |

> [!note] subagent 的代價
> 每個 subagent 也會花自己的 token，而且回傳的摘要仍會佔主 context。所以不是越多越好。

## 自編類題

> [!question] 類題 02-1
> 一個程式碼修改 agent 要處理「把 logging 套件從 A 換成 B」，但事先不知道有哪些檔案用到。哪種設計最合適？
>
> - A. 固定三步驟流程：改 import、改呼叫、跑測試，每步一個 agent
> - B. orchestrator 先搜尋用到 A 的檔案，再為每個檔案或模組動態建立 worker，最後彙整
> - C. 單一 agent 一次讀完整個專案再逐一修改
> - D. 預先為每個資料夾建立一個固定 subagent
>
> > [!tip]- 解析
> > 答案 **B**。要改多少檔案取決於搜尋結果，無法預先寫死，這正是動態拆解的適用情境。A、D 的子任務是事先固定的；C 會把整個專案灌進單一 context。

> [!question] 類題 02-2
> 客服 agent 在自動退款 600 元後，因客戶要求投訴而升級給人工。人工座席接手後又重新處理了一次退款。交接包最應該補上哪一項？
>
> - A. 完整的對話原文
> - B. 結構化欄位，包含「已退款 600 元」這類已執行的動作與授權狀態
> - C. 客戶情緒的描述
> - D. 更長的 system prompt
>
> > [!tip]- 解析
> > 答案 **B**。接手方看不到先前的對話，也不知道已經退過款。結構化交接包要把已執行的動作與授權狀態明確寫出，避免重複操作。A 冗長且重點被埋；C、D 與重複退款無關。

> [!question] 類題 02-3
> 開發者昨天用 Claude Code 分析某模組到一半被中斷，今天要接著做。這段時間同事修改了其中兩個檔案。最合適的做法是？
>
> - A. 續接 session，並直接要求繼續
> - B. 續接 session，告知哪兩個檔案已變更，請針對這兩個檔案重新分析
> - C. 刪掉 session，從零開始
> - D. 續接 session 後，把昨天的所有結果都視為有效
>
> > [!tip]- 解析
> > 答案 **B**。既保留了未變動部分的分析成果，又處理了過期的部分。A、D 假設舊結果仍然正確；C 浪費已完成的工作。

## 備考建議

- **看到「事先不知道有幾個」就想動態拆解**：固定步驟、可預測的才用 workflow。
- **交接題的正解通常是「結構化欄位」**：選項若出現「貼整段對話」或「只寫一句摘要」，多半是陷阱。
- **續接題抓「世界變了沒」**：被中斷的動作要先確認、被改過的檔案要重分析。
- **隔離題抓「誰的 context 被佔用」**：雜訊多就交給 subagent，只收摘要。

## 速查表

| 考點 | 一句話 | 常見錯誤選項 |
|---|---|---|
| 動態拆解 | 子任務由 orchestrator 依輸入決定 | 預先寫死步驟 |
| 委派說明 | 目標、輸出格式、工具、邊界四項都要寫 | 只給一句話 |
| 交接包 | 背景、發現、已執行動作與授權、待決事項 | 貼整段對話原文 |
| 續接 | 先確認被截斷的動作，再針對變更重分析 | 直接重跑、全部視為有效 |
| 隔離 | subagent 獨立 context、只回摘要 | 全部塞進主 context |

> [!tip] 一句話
> 交班時，紙上沒寫的就等於不存在。
