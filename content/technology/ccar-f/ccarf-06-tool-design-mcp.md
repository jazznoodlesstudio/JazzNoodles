## 情境

某客服 agent 有兩個工具：`get_customer` 與 `lookup_order`。描述分別是「取得客戶資料」和「查詢訂單」。使用者說「查一下我的訂單 A1024」，agent 卻三番兩次先呼叫 `get_customer`，並用使用者的姓名亂猜 ID。另外，`lookup_order` 在資料庫連線逾時時只回傳一句 `"error"`，agent 以為訂單不存在，直接告訴客戶「查無此單」。

兩個問題都不在模型，而在**工具的設計**：描述不夠清楚，錯誤沒有分類。

---

## 考點 1：工具描述是模型選工具的主要依據（目標 #27）

### 用樂團來想：樂器上貼的標籤

領班要在臨時指派樂手時，只能靠樂器上的標籤判斷誰該上場。標籤只寫「弦樂」，他分不出小提琴和貝斯。

### 正式一點

模型怎麼選工具，主要看工具的 `name`、`description` 與 `input_schema`。Anthropic 的建議是描述要寫詳細：這個工具做什麼、**什麼時候該用**、**什麼時候不該用**、每個參數代表什麼，以及它回傳什麼。含糊或彼此重疊的描述，是選錯工具最常見的原因。

| 描述寫法 | 效果 |
|---|---|
| 「查詢訂單」 | 太短，模型不知道輸入該用什麼 ID |
| 「用**訂單編號**（格式 A 加四位數）查詢訂單狀態與出貨資訊。使用者提供訂單編號時使用。若只有姓名或電話，**不要使用**，請先用 `get_customer`。回傳狀態、預計到貨日。」 | 輸入格式、使用時機、邊界、回傳內容都清楚 |

三個寫描述的原則：

1. **輸入格式與範例**：參數是什麼、長什麼樣
2. **使用邊界**：和類似工具之間誰負責什麼，明確寫「不要在 X 情況用」
3. **回傳內容**：模型才知道拿到結果後能做什麼

> [!failure] 陷阱 1：兩個工具描述幾乎一樣
> 模型會隨機選，或兩個都呼叫。要改的是**描述**，不是在 system prompt 補一句「優先用 A」。必要時直接合併或改名，讓職責不重疊。

> [!failure] 陷阱 2：把「怎麼用」全塞進 system prompt
> 工具描述會跟著工具走，system prompt 的指示容易和描述互相矛盾或遺漏。工具自己的使用說明放在工具描述裡。

> [!note] 工具太多也是問題
> 可選的工具越多，選錯機率越高。每個 agent 只給它需要的工具，subagent 的工具限制（見 [[ccarf-02-multi-agent|02]]）也是同一個原則。

## 考點 2：MCP 工具出錯時怎麼回報（目標 #26）

兩層錯誤要分清楚：

| 層級 | 例子 | 怎麼處理 |
|---|---|---|
| **協定層錯誤** | 連不上 server、格式錯誤 | 由 client 處理，通常屬於基礎設施問題 |
| **工具執行錯誤** | 資料庫逾時、權限不足、輸入不合法 | 把錯誤放進**工具結果**，標示為錯誤（MCP 用 `isError`；在 Claude API 的 `tool_result` 用 `is_error`），讓模型看得到並作出反應 |

重點是第二列：工具失敗不是丟例外讓整個 agent 當掉，而是把**有資訊的錯誤**交給模型。「有資訊」是指它能分辨該怎麼辦。下面這個分類是我整理的設計做法，不是官方的固定欄位：

| 錯誤類型 | 例子 | 該怎麼做 | 可否重試 |
|---|---|---|---|
| 暫時性（transient） | 逾時、服務暫時不可用 | 稍後重試，有次數上限 | 可 |
| 輸入不合法（validation） | ID 格式錯、缺必要參數 | 修正輸入再試 | 修正後可 |
| 權限（permission） | 沒有存取權 | 不要重試，升級或請求授權 | 不可 |
| 業務規則（business） | 超過退款上限、訂單已結案 | 不要重試，告知使用者或升級 | 不可 |

![[ccarf-06-errors.svg]]

回傳的錯誤至少要包含：**類型、是否可重試、給人看得懂的說明**。這樣情境中的「資料庫逾時」就會被標成可重試的暫時性錯誤，而不是被當成「查無此單」。

另一個容易混淆的點：**「查無資料」不是錯誤**。查詢成功但沒有結果，應回傳明確的空結果（「沒有符合的訂單」），而不是標成錯誤。把兩者混為一談，agent 就分不出是「真的沒有」還是「查詢失敗」。

> [!failure] 陷阱 3：所有失敗都回同一句 `"error"`
> agent 無法判斷要重試、改輸入還是升級。錯誤要分類，並標明可否重試。

> [!failure] 陷阱 4：把逾時當成空結果
> 這會讓 agent 對客戶下錯誤結論（「查無此單」）。逾時是錯誤，不是空結果。

> [!failure] 陷阱 5：不論什麼錯誤都自動重試
> 權限錯誤、業務規則拒絕，重試只會重複失敗，還可能造成重複副作用。只有暫時性錯誤該重試。

## 考點 3：MCP 整合（目標 #28）

MCP（Model Context Protocol）是讓 Claude 連接外部工具與資料來源的開放協定。這個目標的三個考點：

- **範圍**：團隊共用的 server 設在 project 範圍（專案根目錄 `.mcp.json`，進版控）；個人的放 local 或 user。同名時 local ＞ project ＞ user，整份定義取代，欄位不合併。詳見 [[ccarf-04-explore-plan|04]]
- **環境變數展開**：`.mcp.json` 的 `command`、`args`、`env`、`url`、`headers` 支援 `${VAR}` 與 `${VAR:-預設}`，密碼不寫進檔案
- **工具探索**：連上 server 後，它提供的工具會出現在 agent 可用的工具清單，模型依各工具的描述來選用；伺服器端的工具描述品質直接決定模型選得對不對，這點回到考點 1

> [!note] 驗證連線的習慣
> 變數沒設定時，檔案仍會載入，但會用字面上的 `${VAR}`，連線時才失敗。排查連線問題時，先確認環境變數有沒有設、`claude mcp list` 有沒有警告。

## 考點 4：`tool_choice` 與多工具順序（目標 #29）

多步驟流程有時需要**第一步一定要做某件事**，例如先驗證身分才能查資料。`tool_choice` 可以用來控制：

| 需求 | 做法 |
|---|---|
| 第一輪一定要先呼叫 `verify_identity` | 第一次請求用 `{"type": "tool", "name": "verify_identity"}`，之後改回 `auto` |
| 一定要呼叫工具，但可由模型挑 | `{"type": "any"}` |
| 不希望同時呼叫多個 | 加上 `disable_parallel_tool_use` |
| 前一步的結果決定下一步 | 迴圈中逐輪處理，依 `tool_result` 決定 |

要注意：**強制順序要靠程式控制，不能只靠描述請模型「先驗證再查詢」**。如果「未驗證不得查詢」是不能被違反的規則，最可靠的做法是在 PreToolUse hook 或 orchestration 層檢查，而不是只在工具描述寫「請先驗證」（回到 [[ccarf-03-config-layers|03]] 的主題）。

> [!failure] 陷阱 6：用描述保證呼叫順序
> 「請先呼叫 verify_identity」是建議。順序是業務必須遵守的規則時，用 `tool_choice` 強制第一步，並在程式層擋住未驗證的查詢。

## 自編類題

> [!question] 類題 06-1
> 工具 `search_docs`（搜尋文件內容）和 `find_files`（依檔名找檔案）的描述都是「搜尋檔案」，agent 經常選錯。最有效的修正是？
> A. 在 system prompt 加「找內容用 search_docs」
> B. 把兩個工具的描述改為各自說明輸入、用途，並明寫「不適用於…請改用…」
> C. 增加第三個工具協助判斷
> D. 降低 temperature
>
> > [!tip]- 解析
> > 答案 **B**。工具描述是模型選工具的主要依據，問題出在描述重疊。A 容易與描述矛盾，C 增加複雜度，D 不處理根因。

> [!question] 類題 06-2
> 付款 MCP 工具在連線逾時時回傳 `{"error": "failed"}`，agent 因此告訴使用者「付款失敗，請重新操作」，結果使用者重複付款。最合適的改進是？
> A. 讓工具逾時時直接丟例外
> B. 回傳含錯誤類型（transient）、是否可重試、說明的結構化錯誤，並標示為錯誤結果
> C. 在 system prompt 加「遇到錯誤不要重試」
> D. 逾時時回傳空結果
>
> > [!tip]- 解析
> > 答案 **B**。agent 需要資訊來分辨「該重試、該確認、還是該升級」。對付款這類有副作用的操作，還應提供確認狀態的方法，避免重複扣款。D 把錯誤偽裝成空結果，最糟。

> [!question] 類題 06-3
> 流程規定「必須先 `verify_identity`，才能呼叫 `get_account`」，違反會有合規問題。最可靠的做法是？
> A. 在 `get_account` 的描述寫「請先驗證身分」
> B. 在 system prompt 寫三次這個順序
> C. 用程式（hook 或 orchestration 層）在驗證通過前擋下 `get_account`，並以 `tool_choice` 強制第一步
> D. 增加 few-shot 範例
>
> > [!tip]- 解析
> > 答案 **C**。有合規後果的順序要由程式強制，A、B、D 都屬於建議層。

## 備考建議

- **選錯工具先看描述**，不是先改 prompt。
- **錯誤處理題抓三件事**：有沒有分類、有沒有標示可否重試、有沒有把「空結果」和「失敗」分開。
- **順序要保證，就想強制層**：這是整個 Domain 2、3 共同的主線。

## 速查表

| 問題 | 解法 | 常見錯誤選項 |
|---|---|---|
| 模型選錯工具 | 改寫描述：輸入、用途、邊界、回傳 | 在 system prompt 補規則 |
| 工具失敗 | 結構化錯誤：類型、可否重試、說明 | 回 `"error"`、丟例外讓 agent 當掉 |
| 查無資料 | 回明確空結果 | 標成錯誤，或與逾時混為一談 |
| 暫時性錯誤 | 有上限地重試 | 無限重試 |
| 權限／業務規則錯誤 | 不重試，升級或告知 | 自動重試 |
| 團隊共用 MCP | project 範圍、`${VAR}` 帶密碼 | local／user、明文密碼 |
| 必須先做某步 | `tool_choice` 強制第一步＋程式層擋 | 只寫在描述裡 |

> [!tip] 一句話
> 標籤貼清楚，樂手才選得對；出錯要說明白，領班才知道怎麼辦。
